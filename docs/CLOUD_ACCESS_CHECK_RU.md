# Проверка связи: пошагово с телефона

Это инструкция для следующего приезда на дачу или для человека, который сейчас
находится рядом с роутером. Из другого места без настроенного удалённого доступа
подключение к `192.168.1.1` не сработает.

## 1. Что делать с флешкой

**Флешку, на которой уже работает наш сервер, оставить в USB роутера.**
Ничего на неё копировать, распаковывать или устанавливать для этой проверки
не нужно. Не вынимать её и не форматировать. Новая пустая флешка не нужна.

Проверку передадим роутеру прямо через терминал — так не нужны скачивание
файла на роутере, SFTP и доступ роутера к GitHub.

## 2. Сохранить эту инструкцию заранее

Пока интернет работает, сохраните эту страницу или скопируйте весь блок из
шага 5 в заметку, которая открывается без интернета. На даче GitHub и этот
чат могут не открываться.

## 3. Подключить телефон к роутеру

1. На даче откройте на телефоне «Настройки» → «Wi-Fi».
2. Выберите ту сеть, через которую раньше открывали наш сервер
   `http://192.168.1.1:8765/`. Нужна сеть роутера с флешкой.
3. Если телефон пишет «Без доступа к интернету», выберите «Оставаться
   подключённым» или аналогичную кнопку. Для терминала достаточно местного Wi-Fi.
4. Отключите VPN на телефоне на время подключения. Модем и его мобильный
   интернет оставьте в обычном рабочем состоянии: проверяем именно этот путь.

## 4. Открыть знакомый чёрный экран

1. Запустите приложение, из которого раньше присылали фотографии чёрного
   экрана с командами. На ваших фотографиях сохранённое подключение называлось
   **endware**.
2. Нажмите это подключение. Если приложение запросит пароль, введите свой
   прежний пароль SSH/Entware.
3. Дождитесь строки `~ #` и курсора. Вверху обычно написано `BusyBox`.

Это нужное место. Команды вводятся здесь, а не в браузере на странице
`192.168.1.1`, не в интерфейсе обогревателей и не в тестировании Yandex Cloud.

Если подключения endware нет, создайте SSH-подключение с адресом
`192.168.1.1`, портом `222` и пользователем `root`, используя прежний пароль
Entware. Названия кнопок создания зависят от приложения.

Если появляется «Нет соединения»/тайм-аут и строки `~ #` нет, остановитесь
на этом шаге и пришлите текст ошибки: сначала нужно восстановить местное
подключение к роутеру.

## 5. Вставить проверку

1. Скопируйте **весь блок ниже**, начиная с `/opt/bin/sh` и заканчивая
   последней отдельной строкой `HEATBRIDGE_CHECK`. Ничего в нём не заменяйте.
2. Вернитесь в чёрный экран подключения **endware**.
3. Нажмите значок буфера обмена вверху, который виден на ваших фотографиях,
   или удерживайте палец у курсора и выберите «Вставить».
4. Если приложение спрашивает подтверждение вставки нескольких строк,
   подтвердите вставку. Нажмите Enter/«Ввод», если выполнение не началось.
5. Подождите около 40 секунд. Проверка закончена, когда снова появилась
   строка `~ #`. Промежуточные строки с `>` при вставке блока — это нормально.

```sh
/opt/bin/sh <<'HEATBRIDGE_CHECK'
set -u
export PATH=/opt/bin:/opt/sbin:/usr/bin:/bin:/usr/sbin:/sbin
command -v curl >/dev/null 2>&1 || { echo 'curl is required.' >&2; exit 1; }
date -u '+UTC=%Y-%m-%dT%H:%M:%SZ'
if [ -x /opt/etc/init.d/S85heatbridge-alice ]; then
 if /opt/etc/init.d/S85heatbridge-alice status >/dev/null 2>&1; then
  echo 'ALICE_AGENT=RUNNING'
 else
  echo 'ALICE_AGENT=NOT_RUNNING'
 fi
else
 echo 'ALICE_AGENT=STATUS_SCRIPT_MISSING'
fi
failed=0
check() {
 name="$1"
 url="$2"
 if result="$(curl -q --noproxy '*' --proto '=https' \
   --connect-timeout 5 --max-time 8 --head \
   -sS -o /dev/null -w '%{http_code} dns=%{time_namelookup}s connect=%{time_connect}s tls=%{time_appconnect}s total=%{time_total}s' "$url" 2>/dev/null)"; then
  case "$result" in
   [1-5][0-9][0-9]\ *) printf '%s TLS_OK HTTP=%s\n' "$name" "$result";;
   *) printf '%s NO_VALID_HTTP_RESPONSE\n' "$name"; failed=1;;
  esac
 else
  rc=$?
  case "$rc" in
   6) reason=DNS_FAILED;;
   7) reason=CONNECT_FAILED;;
   28) reason=TIMEOUT;;
   35) reason=TLS_FAILED;;
   60) reason=CERTIFICATE_FAILED;;
   *) reason=CURL_FAILED;;
  esac
  printf '%s %s curl_exit=%s\n' "$name" "$reason" "$rc"; failed=1
 fi
}
check CloudFunctions https://functions.yandexcloud.net/
check MessageQueue https://message-queue.api.cloud.yandex.net/
check ObjectStorage https://storage.yandexcloud.net/
check DiskWebDAV https://webdav.yandex.ru/
printf '%s\n' 'This checks endpoint access only; account permissions and actual delivery are not tested.'
exit "$failed"
HEATBRIDGE_CHECK
```

## 6. Где смотреть и что прислать

Результат появится **на этом же чёрном экране**. Прокрутите немного вверх:
нужен участок от `UTC=...` до последней строки проверки. Сделайте снимок
экрана; если всё не помещается — два снимка. Или выделите и скопируйте этот
участок текстом в наш чат.

Там будут строки с такими названиями:

| Строка | Что проверили |
|---|---|
| `ALICE_AGENT` | Запущена ли программа связи с Алисой |
| `CloudFunctions` | Доступ к адресу облачных функций |
| `MessageQueue` | Доступ к адресу очереди команд |
| `ObjectStorage` | Доступ к адресу хранилища подтверждений |
| `DiskWebDAV` | Доступ к WebDAV Яндекс Диска — кандидату на другой канал |

Вместе с результатом напишите: «Проверял на даче, Билайн, ограничения сейчас
есть / нет / не знаю». Не нужно менять температуру для этого теста.

Проверка не меняет настройки, не перезапускает программы и не управляет
обогревателями. Она не выводит пароли и ключи. После неё можно просто закрыть
терминал. Флешка остаётся в роутере.

## Как читать результат

- `ALICE_AGENT=RUNNING`: процесс агента найден. Это ещё не подтверждает его
  успешную работу с очередью.
- `ALICE_AGENT=NOT_RUNNING`: процесс не найден; сначала нужно выяснить,
  почему он остановился. Это не доказательство блокировки сети.
- `TLS_OK HTTP=...`: адрес отвечает по HTTPS с проверенным сертификатом.
  Даже 401, 403 или 404 подтверждают доступ к адресу, но не доступ к вашим
  данным и не возможность отправлять команды.
- `DNS_FAILED`, `CONNECT_FAILED`, `TIMEOUT`, `TLS_FAILED` или
  `CERTIFICATE_FAILED`: этап ошибки. Причину уточняют отдельно; одна такая
  ошибка сама по себе не доказывает фильтрацию оператором.

Проверяются Cloud Functions, Message Queue, Object Storage и WebDAV Диска.
Для сравнения полезно повторить проверку после снятия ограничений в той же сети.

Если текущие облачные адреса недоступны, а WebDAV отвечает, следующий шаг —
проверить запись и чтение отдельного тестового файла через WebDAV. До этого
не переносим управление отоплением на Диск и не покупаем VPS. Наличие Диска
в списке доступных приложений не гарантирует работу его WebDAV API.
